# Engineering problems and fixes

This is a postmortem-style summary of the main performance and correctness problems encountered while building SIRIUS and the design changes used to contain them.

| Problem | What users saw | Root cause | Fix | Protection |
|---|---|---|---|---|
| Resource usage was high | Slow startup and too many database reads | Unbounded selects, repeated full question loads, and optional assets competing with first paint | Paged reads, known-count page waves, compact snapshots, version fingerprints, lazy answer data, and idle warming for secondary assets | Performance and concurrency tests |
| Images took too long to load | Large or inconsistent images, especially from external Drive links | Original files were larger than the card needed; repeated stimulus images were requested more than once | Thumbnail normalization, validated local migration, bounded WebP conversion, dimensions, async decoding, current-plus-next-image preload, and deduplication | Image migration and offline-image tests |
| The service worker broke external images | A Drive image failed quickly while the page itself worked | The worker tried to fetch cross-origin images under a same-origin CSP | Same-origin guard; cross-origin images return to the browser's native path | Image-hosting regression coverage |
| The first visit downloaded too much | The shell was waiting on legal pages, large icons, and optional artwork | Every asset was treated as install-critical | Small app-shell install list; secondary assets warm after idle or a bounded delay | Performance-loading tests |
| Long quizzes felt heavy | Scrolling and results review became slow on phones | Too many question cards were created in one DOM operation | Render batches of 15, an `IntersectionObserver` sentinel, and `DocumentFragment` insertion | Scroll and student-navigation tests |
| The leaderboard could hang | An endless loading state after a slow ranking response | Peer data waited on unrelated synchronization and had no bounded fetch outcome | Sync gate timeout, fetch timeout, in-flight promise coalescing, cached-first paint, retryable empty state, and render-on-change only | Peer-page performance tests |
| Leaderboard and bookmarks interfered with each other | One failed panel made the other look empty or caused unnecessary work | Both datasets were loaded and committed as one operation | Section-specific loading, separate fetched timestamps, partial-success preservation, and separate cache projections | Community and peer tests |
| Bookmarks became stale or appeared to overlap | A removed bookmark could return after another sync; equal rows could jump | Arrays were merged as append-only and peer refreshes raced with local mutations | Set semantics for personal bookmarks, version-aware optimistic sync, force refresh after a successful mutation, question-id keyed aggregate counts, and stable id tie-breaks | Study-sync and community-bookmark tests |
| Large question/answer payloads were expensive | Sessions loaded more content than the current view needed | Full answer keys and stimulus data were fetched eagerly | Question snapshot first, answer data only for the active session, stimulus ids deduplicated and chunked, bounded prefetch | Question-bank and performance tests |
| Offline image downloads consumed storage or could not stop | Downloads repeated work or continued after the student cancelled | No separate package boundary or progress-aware loop | Separate offline cache, skip existing URLs, progress, cancellation, quota handling, and module-level scope | Offline-question-image tests |
| PDF export retained memory | Repeated exports accumulated temporary image resources | Blob/object URLs were not always released after printing | Unique image URL collection, small load waves, print-only object URLs, and guaranteed revocation | PDF export tests |
| A content edit could break saved progress | Changing visible wording disconnected bookmarks and history | Display text was being treated as identity | Stable question and stimulus ids separate content identity from wording; duplicate filtering is explicit and deterministic | Duplicate, migration, and question-bank tests |

The public code examples intentionally model only the safe algorithmic parts. They do not include production credentials, user rows, private endpoints, or administrative operations.
