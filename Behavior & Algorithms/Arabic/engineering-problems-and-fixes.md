# أبرز المشاكل والحلول

هذا ملخص شبيه بتقرير postmortem لأهم مشاكل الأداء والصحة التي ظهرت أثناء بناء SIRIUS، وما تم تغييره لعلاجها.

| المشكلة | ما كان يراه المستخدم | السبب | الحل | الحماية |
|---|---|---|---|---|
| استهلاك الـresources كان عاليًا | بداية بطيئة وقراءات كثيرة من قاعدة البيانات | استدعاءات بلا pagination وتحميل بنك الأسئلة كاملًا أكثر من مرة وملفات اختيارية تنافس أول paint | تقسيم الصفوف، waves بعدد معروف، snapshot مختصر، version fingerprint، تحميل answer data عند الحاجة، وتسخين الملفات الاختيارية وقت الخمول | اختبارات الأداء والـconcurrency |
| الصور كانت بطيئة | صور كبيرة أو غير ثابتة، خصوصًا روابط Drive الخارجية | الملف الأصلي أكبر من احتياج الكارت، وصورة الـstimulus كانت تتكرر مع كل سؤال | تحويل الرابط إلى thumbnail، نقل آمن للتخزين المحلي، تحويل WebP بحدود، تثبيت الأبعاد، decoding غير متزامن، preload للصورة الحالية والقادمة، وإزالة التكرار | اختبارات image migration والـoffline |
| الـservice worker كان يكسر الصور الخارجية | صورة Drive تفشل بسرعة رغم أن الصفحة تعمل | الـworker كان يحاول جلب صورة cross-origin تحت CSP same-origin | same-origin guard وترك الصور الخارجية لمسار المتصفح الطبيعي | اختبارات image-hosting |
| أول زيارة كانت تحمل ملفات كثيرة | الـshell ينتظر صفحات قانونية وأيقونات وفن اختياري | كل الملفات كانت تعتبر ضرورية للتثبيت الأول | قائمة app-shell صغيرة، وتسخين الملفات الثانوية بعد idle أو تأخير محدود | اختبارات performance-loading |
| الكويز الطويل كان ثقيلًا | scroll والنتائج يتأخران على الهاتف | إنشاء عدد كبير من كروت الأسئلة في عملية DOM واحدة | batches من 15 سؤالًا، sentinel مع `IntersectionObserver`، وإدخال كل دفعة عبر `DocumentFragment` | اختبارات scroll وstudent-navigation |
| الليدر بورد كان يعلق | loading مستمر بعد بطء طلب الترتيب | انتظار sync غير متعلق بالصفحة، مع عدم وجود حد زمني للطلب | timeout للـsync، timeout للـfetch، coalescing للـpromise، عرض الكاش أولًا، وحالة قابلة لإعادة المحاولة مع إعادة الرسم عند التغير فقط | اختبارات peer-page performance |
| الليدر بورد والبوك ماركس كانوا يؤثرون على بعض | فشل جزء يجعل الجزء الآخر يبدو فارغًا أو يسبب شغلًا زائدًا | تحميل البيانات وعرضها كعملية واحدة | تحميل كل قسم منفصلًا، timestamps منفصلة، الحفاظ على الجزء الناجح، وcache projections مستقلة | اختبارات community والـpeer |
| البوك ماركس كانت تدخل في بعضها أو ترجع بعد حذفها | bookmark محذوف يظهر بعد sync آخر، والصفوف المتساوية تتحرك | دمج arrays كأنها append-only وتنافس refresh مع التعديل المحلي | Set semantics للبوك ماركس الشخصية، optimistic sync مع version، force refresh بعد نجاح التعديل، counters حسب `question_id`، وكاسر تعادل ثابت بالـid | اختبارات study-sync وcommunity-bookmarks |
| payload الأسئلة والإجابات كان كبيرًا | تحميل محتوى أكثر من المطلوب للشاشة الحالية | جلب answer keys وبيانات الـstimuli كلها مبكرًا | question snapshot أولًا، answer data للجلسة المطلوبة فقط، تقسيم stimulus ids، وprefetch محدود | اختبارات question-bank والأداء |
| تحميل صور الـoffline كان يستهلك مساحة أو لا يتوقف | تكرار التحميل أو استمرار العملية بعد cancel | عدم وجود حدود منفصلة للحزمة وعدم وجود loop واعٍ بالتقدم | cache مستقل للـoffline، تخطي الموجود، progress، cancel، التعامل مع quota، وتحديد الحزمة بالموديول | اختبارات offline-question-images |
| تصدير الـPDF كان يراكم الذاكرة | exports متتالية تترك موارد صور مؤقتة | عدم تحرير object URLs دائمًا بعد الطباعة | جمع الروابط المختلفة، waves صغيرة، object URLs للتصدير فقط، وrevocation مضمون | اختبارات PDF export |
| تعديل السؤال كان يفصل تقدمه القديم | تغيير النص يفصل الـbookmark والـhistory | اعتبار النص الظاهر هو هوية السؤال | استخدام `question.id` و`stimulus.id` ثابتين وفصل الهوية عن النص، مع duplicate filtering حتمي | اختبارات duplicate والـquestion-bank |

الأمثلة المنشورة تشرح الأجزاء الخوارزمية الآمنة فقط، ولا تحتوي على credentials أو صفوف مستخدمين أو endpoints خاصة أو عمليات إدارية.
